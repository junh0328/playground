## 들어가며

요즘 많은 회사들의 채용 공고에 기술 과제 항목이 포함되고 있습니다. 체감상 이전보다 많은 회사에서 기술 과제를 프로세스에 포함하고 있는 것 같은데요, 적게는 8시간, 2일 많게는 7일 정도의 시간을 부여받습니다.

이렇게 제한된 시간에서 요구사항을 완료하고, 코드를 구현할 때, 스스로 '어느 정도 수준까지 개발을 해야 하나'를 되묻게 되었습니다. Claude Skills에 관심을 갖게 된 요즘, CTO급 상황을 가정한 나의 코드 기술 과제 평가 도우미를 만들어 보았습니다.

> 완성된 스킬 파일은 [GitHub](https://github.com/junh0328/playground/tree/main/content/skills/cto-assignment-reviewer)에 올려두었습니다. 먼저 확인하고 싶은 분들은 파일을 다운로드 받아 직접 실행해보세요.

> **Skills 기초 개념**이 필요하다면 이전 글을 먼저 참고하세요:
> [Claude Agent Skills 톺아보기 - 기술 블로그 글쓰기 도우미 Skill 만들기](https://junheedot.tistory.com/entry/Claude-Agent-Skills-%ED%86%BA%EC%95%84%EB%B3%B4%EA%B8%B0-%EA%B8%B0%EC%88%A0-%EB%B8%94%EB%A1%9C%EA%B7%B8-%EA%B8%80%EC%93%B0%EA%B8%B0-%EB%8F%84%EC%9A%B0%EB%AF%B8-Skill-%EB%A7%8C%EB%93%A4%EA%B8%B0)

## 최종 결과물

완성된 스킬을 사용하면 다음과 같이 과제를 평가할 수 있습니다:

```bash
# 자연어로 요청 (Skills는 자동으로 컨텍스트에 로드됨)
> "이 과제를 평가해줘. 2일의 기한을 둔 과제야."

# 또는 슬래시 명령어로 호출 (Commands 설정 시)
> /cto-review
```

평가 결과로 종합 점수, 카테고리별 분석, 레드 플래그, 면접 질문 제안까지 포함된 상세 리포트를 받을 수 있습니다.

> **참고**: 슬래시 명령어(`/`)로 호출하려면 Skills 외에 Commands도 만들어야 합니다. 이 글 마지막에 Commands 설정 방법을 설명합니다.

## 1단계: 스킬 폴더 구조 생성

스킬은 `~/.claude/skills/` 또는 프로젝트의 `.claude/skills/` 폴더에 생성합니다.

```bash
# 사용자 전역 스킬 (모든 프로젝트에서 사용)
mkdir -p ~/.claude/skills/cto-assignment-reviewer/references

# 또는 프로젝트별 스킬 (해당 프로젝트에서만 사용)
mkdir -p .claude/skills/cto-assignment-reviewer/references
```

### 폴더 구조

```
cto-assignment-reviewer/
├── SKILL.md                      # 메인 스킬 정의
└── references/
    ├── checklist.md              # 상세 체크리스트
    ├── report-template.md        # 리포트 템플릿
    └── interview-questions.md    # 면접 질문 뱅크
```

## 2단계: SKILL.md 작성

`SKILL.md`는 스킬의 핵심 파일입니다. YAML 프론트매터로 메타 정보를 정의하고, 본문에 상세 가이드를 작성합니다.

### 프론트매터 작성

```markdown
---
name: cto-assignment-reviewer
description: |
  CTO 수준의 프론트엔드 과제 평가 도우미. 채용 과제를 체계적으로 분석하고 객관적인 평가 리포트를 생성합니다.
  이 스킬은 다음 상황에서 사용하세요:
  - 프론트엔드 채용 과제를 평가할 때
  - 코드 품질, 아키텍처, 테스트 전략을 분석할 때
  - 제한시간(2일/7일)에 따른 기대치 조정이 필요할 때
  - 객관적인 채용 판단 근거가 필요할 때
---
```

> **팁**: `description`은 Claude가 이 스킬을 언제 사용할지 판단하는 기준이 됩니다. 구체적인 사용 상황을 명시하세요.

### 핵심 원칙 정의

스킬이 따라야 할 원칙을 명확히 정의합니다:

```markdown
## 핵심 원칙

1. **객관성**: 개인 취향이 아닌 업계 표준 기준으로 평가
2. **공정성**: 제한시간과 요구사항 수준을 고려한 기대치 조정
3. **건설성**: 단순 비판이 아닌 구체적 개선 방향 제시
4. **일관성**: 모든 과제에 동일한 기준 적용
5. **과유불급**: 요구사항을 넘어선 과도한 구현은 오히려 감점 요소
```

### Quick Check 섹션

빠른 평가를 위한 체크리스트를 제공합니다:

```markdown
## Quick Check (빠른 평가용)

**5분 안에 확인하는 핵심 10개 항목:**

| #   | 항목                 | 확인 방법                  | Pass/Fail               |
| --- | -------------------- | -------------------------- | ----------------------- |
| 1   | **실행 가능**        | `yarn install && yarn dev` | 에러 없이 실행          |
| 2   | **핵심 기능 동작**   | 요구사항 체크리스트 대조   | 필수 기능 모두 동작     |
| 3   | **any 타입 남용**    | `grep -r "any" src/`       | 5개 미만                |
| 4   | **폴더 구조 적정성** | `tree src/`                | 파일 1개 폴더 반복 없음 |
| 5   | **불필요한 코드**    | 요구사항 대비 구현 범위    | 과잉 구현 없음          |
```

## 3단계: 평가 워크플로우 정의

Claude가 따라야 할 단계별 워크플로우를 정의합니다:

```markdown
## 평가 워크플로우

### 1단계: 컨텍스트 파악

평가 시작 전 확인할 사항:

- 제한시간 (2일 / 7일 / 무제한)
- 요구사항 문서 (README, 과제 명세)
- 기술 스택 제약
- 평가 목적 (주니어/시니어)

**사용자에게 질문**:

- "과제 제한시간이 얼마였나요?"
- "지원자의 예상 레벨이 어떻게 되나요?"

### 2단계: 코드베이스 탐색

다음 파일들을 우선 확인:
| 파일 | 확인 목적 |
|------|----------|
| `package.json` | 의존성, 스크립트 구성 |
| `README.md` | 실행 방법, 의사결정 기록 |
| `tsconfig.json` | TypeScript 엄격도 |
| `src/` 구조 | 폴더 아키텍처 |

### 3단계: 심층 분석

references/checklist.md의 체크리스트에 따라 평가 진행.

### 4단계: 리포트 생성

references/report-template.md 형식으로 최종 리포트 작성.
```

## 4단계: 제한시간별 가중치 설정

과제 제한시간에 따라 평가 기준이 달라야 합니다:

### 2일 과제 (48시간)

```markdown
### 2일 과제 가중치

**핵심**: 기본기 + 우선순위 판단력

| 항목        | 가중치 | 기대 수준                |
| ----------- | ------ | ------------------------ |
| 기능 완성도 | 35%    | 핵심 기능 동작 필수      |
| 코드 품질   | 30%    | 타입 안정성, 기본 구조화 |
| 코드 적정성 | 15%    | 불필요한 코드 없음       |
| 에러 처리   | 10%    | 최소한의 핸들링          |
| 실행 가능성 | 10%    | 바로 실행 가능           |

**봐주는 것**: 테스트 부족, 문서화 간소
**감점 유지**: 핵심 기능 미완성, any 남발
```

### 7일 과제 (168시간)

```markdown
### 7일 과제 가중치

**핵심**: 프로덕션 레벨 완성도

| 항목        | 가중치 | 기대 수준                  |
| ----------- | ------ | -------------------------- |
| 기능 완성도 | 25%    | 모든 요구사항 + 엣지케이스 |
| 코드 품질   | 20%    | 아키텍처, 패턴, 확장성     |
| 에러 처리   | 15%    | 계층화된 처리              |
| 테스트      | 10%    | E2E + 주요 단위 테스트     |
| 성능        | 10%    | 메모이제이션, 대량 데이터  |
```

## 5단계: 레드 플래그 정의

즉시 감점되어야 하는 항목을 명확히 정의합니다:

```markdown
## 레드 플래그 (즉시 감점)

### 기본 레드 플래그

| 항목                  | 감점   | 이유                 |
| --------------------- | ------ | -------------------- |
| `any` 타입 5개 이상   | -1점   | TypeScript 이해 부족 |
| `eslint-disable` 다수 | -1점   | 코드 품질 경시       |
| 콘솔 에러/경고 방치   | -0.5점 | 디버깅 습관 부재     |
| node_modules 커밋     | -1점   | Git 기본기 부족      |
| 핵심 기능 미완성      | -2점   | 요구사항 미충족      |

### 과잉 구현 레드 플래그

| 항목                    | 감점   | 이유               |
| ----------------------- | ------ | ------------------ |
| 요구사항 무관 기능 과다 | -0.5점 | 요구사항 이해 부족 |
| 과도한 추상화           | -0.5점 | 불필요한 복잡성    |
| 50개 이상의 테스트      | -0.5점 | 시간 배분 실패     |
```

> **주의**: "많이 구현하면 좋다"는 것은 오해입니다. 요구사항에 맞는 적정 수준의 구현이 좋은 평가를 받습니다.

## 6단계: 참조 문서 작성

### checklist.md - 상세 체크리스트

```markdown
# 과제 평가 상세 체크리스트

## 0. 코드 적정성 (최우선 확인)

### 불필요한 코드 여부

- [ ] 요구사항에 명시되지 않은 기능을 과도하게 구현하지 않았는가?
- [ ] 파일 1개뿐인 폴더에 index.ts 배럴 파일을 만들지 않았는가?
- [ ] 10줄 미만의 로직을 별도 커스텀 훅으로 분리하지 않았는가?

### API 활용 방식 (Mock API 제공 시)

- [ ] 서버가 제공하는 필터링 기능을 활용했는가?
- [ ] 서버가 제공하는 정렬/페이지네이션을 활용했는가?
- [ ] 클라이언트에서 filter(), sort()로 재구현하지 않았는가?
```

### report-template.md - 리포트 템플릿

```markdown
# [프로젝트명] 과제 평가 리포트

## 메타 정보

| 항목            | 내용                       |
| --------------- | -------------------------- |
| **지원 포지션** | 프론트엔드 [주니어/시니어] |
| **제한시간**    | [X]일                      |
| **평가일**      | YYYY-MM-DD                 |

## 종합 점수: X.X / 10

| 등급 | 점수 범위 | 의미           |
| ---- | --------- | -------------- |
| S    | 9.0-10.0  | 즉시 채용 권장 |
| A    | 8.0-8.9   | 채용 권장      |
| B    | 7.0-7.9   | 조건부 권장    |
| C    | 6.0-6.9   | 추가 검증 필요 |
| D    | 5.0-5.9   | 보류 권장      |
| F    | 0-4.9     | 비추천         |
```

### interview-questions.md - 면접 질문 뱅크

```markdown
# 면접 질문 뱅크

## 평가 기호 안내

| 기호              | 의미                        |
| ----------------- | --------------------------- |
| ✅ **기대**       | 답변에 포함되어야 할 키워드 |
| ⭐ **가산**       | 언급하면 플러스 포인트      |
| ❌ **레드플래그** | 역량 부족 신호              |

## TypeScript 관련

### 기본

- "any 타입을 사용하지 않으려면 어떻게 해야 할까요?"
  - ✅ **기대**: unknown 타입, 타입 가드, 제네릭 활용
  - ❌ **레드플래그**: "any가 편해서 자주 씀"
```

## 7단계: 스킬 테스트

스킬이 잘 동작하는지 테스트합니다:

```bash
# Claude Code 실행
claude

# 자연어로 요청 (Skills는 자동으로 컨텍스트에 로드됨)
> "이 프로젝트 폴더의 과제를 평가해줘. 2일 과제고 주니어 포지션이야."
```

Skills는 Claude Code가 시작될 때 자동으로 로드됩니다. 별도의 호출 없이 관련 주제를 요청하면 Claude가 해당 스킬의 지식을 활용합니다.

### 스킬 사용 확인 화면

자연어로 과제 평가를 요청하면, Claude가 관련 스킬을 찾아 사용 여부를 확인합니다:

"Yes"를 선택하면 스킬에 정의된 워크플로우에 따라 평가가 진행됩니다.

### 스킬 로드 및 평가 진행

스킬이 로드되면 Claude는 정의된 평가 기준에 따라 체계적으로 분석합니다:

<img src="./content/assets/cto-review-confirm.png" alt="스킬 로드 확인 - 평가 워크플로우, 가중치, 카테고리, 레드 플래그 등이 적용된 모습" />

스킬에 정의된 평가 워크플로우, 2일 과제 가중치, 평가 카테고리, 레드 플래그 항목, 리포트 출력 형식이 모두 적용되어 일관된 평가가 이루어집니다.

### 예상 동작

1. Claude가 `cto-assignment-reviewer` 스킬을 참조합니다.
2. 제한시간과 포지션 레벨을 확인합니다.
3. `package.json`, `README.md`, `src/` 구조를 탐색합니다.
4. 체크리스트 기반으로 심층 분석을 수행합니다.
5. 리포트 템플릿 형식으로 결과를 출력합니다.

## 실제 평가 리포트 예시

```markdown
# todo-app 과제 평가 리포트

## 메타 정보

| 항목            | 내용              |
| --------------- | ----------------- |
| **지원 포지션** | 프론트엔드 주니어 |
| **제한시간**    | 2일               |
| **평가일**      | 2025-01-09        |

## 종합 점수: 7.2 / 10 (B등급)

### 카테고리별 점수

| 카테고리    | 점수 | 가중치 | 기여도 |
| ----------- | ---- | ------ | ------ |
| 기능 완성도 | 8/10 | 35%    | 2.8    |
| 코드 품질   | 7/10 | 30%    | 2.1    |
```

## Commands로 슬래시 명령어 만들기

Skills만으로도 충분하지만, `/cto-review`처럼 슬래시 명령어로 호출하고 싶다면 **Commands**를 추가로 만들어야 합니다.

### Commands 폴더 생성

```bash
# 사용자 전역 Commands
mkdir -p ~/.claude/commands

# 또는 프로젝트별 Commands
mkdir -p .claude/commands
```

### Command 파일 작성

`~/.claude/commands/cto-review.md` 파일을 생성합니다:

```markdown
---
description: CTO 수준의 프론트엔드 과제 평가를 수행합니다
---

현재 프로젝트의 프론트엔드 과제를 CTO 관점에서 평가해주세요.

다음 정보를 먼저 확인해주세요:

1. 과제 제한시간 (2일 / 7일)
2. 지원자 레벨 (주니어 / 미드 / 시니어)

그 후 cto-assignment-reviewer 스킬의 워크플로우에 따라 평가를 진행하고,
리포트 템플릿 형식으로 결과를 출력해주세요.
```

### 사용 방법

```bash
# Claude Code에서 슬래시 명령어로 호출
> /cto-review
```

Commands를 설정하면 `/c`만 입력해도 자동완성 목록에 표시됩니다:

<img src="./content/assets/cto-review-command.png" alt="슬래시 명령어 자동완성 - /cto-review 명령어가 목록에 표시된 모습" />

이제 슬래시 명령어가 실행되면, Claude가 Skills에 정의된 지식을 활용하여 과제를 평가합니다.

### Skills + Commands 조합의 장점

| 구분         | 역할                                                    |
| ------------ | ------------------------------------------------------- |
| **Skills**   | 도메인 지식 저장소 (체크리스트, 가중치, 레드 플래그 등) |
| **Commands** | 진입점 (슬래시 명령어로 빠른 호출)                      |

Skills에 지식을 저장하고, Commands로 호출하면 두 기능의 장점을 모두 활용할 수 있습니다.

## 정리

이 글에서 다룬 내용을 정리합니다:

1. **핵심 원칙 정의**: 객관성, 공정성, 건설성, 일관성, 과유불급
2. **Quick Check**: 5분 안에 확인하는 핵심 10개 항목
3. **평가 워크플로우**: 컨텍스트 파악 → 코드베이스 탐색 → 심층 분석 → 리포트 생성
4. **제한시간별 가중치**: 2일/7일 과제에 따른 기대 수준 차등 적용
5. **레드 플래그**: 즉시 감점 항목 명확화 (any 남발, 과잉 구현 등)
6. **참조 문서 분리**: 체크리스트, 리포트 템플릿, 면접 질문 뱅크
7. **Skills + Commands**: 지식 저장소와 빠른 호출의 조합

Skills를 잘 활용하면 반복적인 업무를 체계화하고, AI의 도움을 더 효과적으로 받을 수 있습니다. 채용 과제 평가 외에도 코드 리뷰, 문서 작성, 기술 면접 등 다양한 도메인에 적용해 보세요.
