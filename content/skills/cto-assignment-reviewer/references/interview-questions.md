# 면접 질문 뱅크

과제 평가 결과에 따라 적절한 질문을 선택하여 면접에서 활용합니다.

## 평가 기호 안내

| 기호 | 의미 |
|------|------|
| ✅ **기대** | 답변에 포함되어야 할 키워드/개념 |
| ⭐ **가산** | 언급하면 플러스 포인트 |
| ❌ **레드플래그** | 역량 부족 신호 |

## 1. TypeScript 관련

### 기본

- "TypeScript를 사용하면서 가장 유용하다고 느끼는 기능은 무엇인가요?"
  - ✅ **기대**: 컴파일 타임 에러 감지, IDE 자동완성, 타입 추론, 리팩토링 안전성
  - ⭐ **가산**: 협업 시 코드 문서화 효과, 런타임 에러 사전 방지
  - ❌ **레드플래그**: "잘 모르겠다", "회사에서 쓰라고 해서", "any 쓰면 편함"

- "any 타입을 사용하지 않으려면 어떻게 해야 할까요?"
  - ✅ **기대**: unknown 타입 사용, 타입 가드, 제네릭 활용, 점진적 타입 정의
  - ⭐ **가산**: strict 모드 설정, as const 활용
  - ❌ **레드플래그**: "any가 편해서 자주 씀", 구체적 대안 없음

- "interface와 type의 차이점을 설명해주세요."
  - ✅ **기대**: interface는 확장(extends) 가능, type은 유니온/인터섹션 가능, interface는 선언 병합
  - ⭐ **가산**: 객체는 interface, 유니온은 type 권장하는 컨벤션 언급
  - ❌ **레드플래그**: "같은 거 아닌가요?", 차이점 설명 못함

### 중급

- "제네릭을 언제 사용하는 것이 좋을까요? 예시를 들어주세요."
  - ✅ **기대**: 재사용 가능한 컴포넌트/함수, 타입 안전성 유지하면서 유연성 확보
  - ✅ **예시 기대**: `useState<T>`, API 응답 래퍼, 리스트 컴포넌트
  - ❌ **레드플래그**: 제네릭 개념 모름, 예시 못 듦

- "타입 가드를 구현해보신 적 있으신가요? 어떤 상황에서 사용하셨나요?"
  - ✅ **기대**: typeof, instanceof, in 연산자, 사용자 정의 타입 가드 (is 키워드)
  - ✅ **예시 기대**: API 응답 타입 분기, 에러 타입 체크
  - ❌ **레드플래그**: 타입 가드 개념 모름, as로 강제 캐스팅만 사용

- "유니온 타입과 인터섹션 타입의 차이를 설명해주세요."
  - ✅ **기대**: 유니온(`|`)은 OR, 인터섹션(`&`)은 AND
  - ✅ **예시 기대**: 유니온 - Status 타입, 인터섹션 - Props 합성
  - ❌ **레드플래그**: 개념 혼동, 사용 경험 없음

### 고급

- "조건부 타입을 활용해본 경험이 있으신가요?"
  - ✅ **기대**: `T extends U ? X : Y` 문법, infer 키워드
  - ⭐ **가산**: Exclude, Extract, ReturnType 등 유틸리티 타입 원리 설명
  - ❌ **레드플래그**: 조건부 타입 개념 모름 (시니어 포지션의 경우)

- "타입 추론을 활용해서 코드를 개선한 경험을 공유해주세요."
  - ✅ **기대**: 불필요한 타입 어노테이션 제거, as const로 리터럴 타입 추론
  - ⭐ **가산**: 함수 반환 타입 추론 활용, 제네릭 기본값 설정
  - ❌ **레드플래그**: 모든 곳에 타입 명시, 추론 활용 안 함

- "외부 라이브러리의 타입이 부족할 때 어떻게 해결하셨나요?"
  - ✅ **기대**: @types 패키지 확인, d.ts 파일 작성, 모듈 확장(declare module)
  - ⭐ **가산**: DefinitelyTyped 기여 경험, 타입 오버라이드 전략
  - ❌ **레드플래그**: "any로 처리", 해결 방법 모름

## 2. React 관련

### 컴포넌트 설계

- "컴포넌트를 분리하는 기준이 무엇인가요?"
  - ✅ **기대**: 단일 책임 원칙, 재사용성, 테스트 용이성, 가독성
  - ⭐ **가산**: 도메인 기준 분리, 합성 패턴 언급
  - ❌ **레드플래그**: "파일이 길어지면", 명확한 기준 없음

- "Props drilling이 심해질 때 어떻게 해결하시나요?"
  - ✅ **기대**: Context API, 상태 관리 라이브러리, 컴포넌트 합성
  - ⭐ **가산**: 각 방법의 트레이드오프 설명, 상황별 선택 기준
  - ❌ **레드플래그**: Props drilling 개념 모름, 해결책 모름

- "재사용 가능한 컴포넌트를 만들 때 고려하는 점은 무엇인가요?"
  - ✅ **기대**: Props 인터페이스 설계, 기본값, 확장 가능한 구조, children 활용
  - ⭐ **가산**: 합성 패턴, Render Props, Headless 컴포넌트
  - ❌ **레드플래그**: 재사용 경험 없음, 하드코딩 습관

### Hooks

- "useEffect의 의존성 배열이 왜 중요한가요?"
  - ✅ **기대**: 무한 루프 방지, 불필요한 실행 방지, 클로저 문제 해결
  - ⭐ **가산**: exhaustive-deps 린트 규칙, 의존성 최소화 전략
  - ❌ **레드플래그**: "빈 배열 넣으면 됨", 의존성 이해 부족

- "useMemo와 useCallback의 차이점과 사용 시점을 설명해주세요."
  - ✅ **기대**: useMemo는 값, useCallback은 함수 메모이제이션
  - ✅ **사용 시점**: 비싼 연산, 참조 동일성 유지, 자식 컴포넌트 최적화
  - ❌ **레드플래그**: 무조건 사용, 차이점 모름, 과도한 최적화

- "커스텀 훅을 만들어 본 경험이 있으신가요? 어떤 상황에서 만드셨나요?"
  - ✅ **기대**: 로직 재사용, 관심사 분리, 테스트 용이성
  - ✅ **예시 기대**: useForm, useFetch, useLocalStorage, useDebounce
  - ❌ **레드플래그**: 만들어본 적 없음, "그냥 컴포넌트에 씀"

- "useRef를 어떤 상황에서 사용하시나요?"
  - ✅ **기대**: DOM 접근, 값 저장(리렌더 안 함), 이전 값 기억
  - ⭐ **가산**: forwardRef와 조합, 인터벌/타이머 관리
  - ❌ **레드플래그**: DOM 접근만 알고 있음, 값 저장 용도 모름

### 상태 관리

- "로컬 상태와 전역 상태를 어떻게 구분하시나요?"
  - ✅ **기대**: 여러 컴포넌트 공유 여부, 서버 상태 vs UI 상태
  - ⭐ **가산**: "가능한 로컬로", 상태 끌어올리기 원칙
  - ❌ **레드플래그**: 모든 것을 전역으로, 구분 기준 없음

- "상태 관리 라이브러리를 선택할 때 고려하는 점은 무엇인가요?"
  - ✅ **기대**: 프로젝트 규모, 러닝 커브, 보일러플레이트, 번들 사이즈
  - ⭐ **가산**: Redux vs Zustand vs Jotai 비교, 서버 상태는 React Query
  - ❌ **레드플래그**: "Redux만 알아요", 선택 기준 없음

- "불변성을 유지하는 것이 왜 중요한가요?"
  - ✅ **기대**: React 렌더링 최적화, 참조 비교, 예측 가능한 상태 변화
  - ⭐ **가산**: Immer 활용, 구조적 공유 개념
  - ❌ **레드플래그**: 불변성 개념 모름, 직접 수정 습관

### 성능

- "React에서 불필요한 리렌더링을 방지하는 방법을 알려주세요."
  - ✅ **기대**: React.memo, useMemo, useCallback, 상태 분리
  - ⭐ **가산**: React DevTools Profiler 사용, 리렌더링 원인 분석
  - ❌ **레드플래그**: 방법 모름, "성능 문제 겪어본 적 없음"

- "React.memo를 언제 사용하는 것이 좋을까요?"
  - ✅ **기대**: 같은 props로 자주 리렌더되는 컴포넌트, 비싼 렌더링
  - ⭐ **가산**: 커스텀 비교 함수, memo 오버헤드 인지
  - ❌ **레드플래그**: 모든 컴포넌트에 적용, 사용 시점 모름

- "대량의 데이터를 렌더링할 때 어떻게 최적화하시나요?"
  - ✅ **기대**: 가상화(react-window, react-virtualized), 페이지네이션, 무한 스크롤
  - ⭐ **가산**: windowing 원리 설명, 실제 적용 경험
  - ❌ **레드플래그**: 최적화 방법 모름, "다 렌더링하면 됨"

## 3. 에러 처리 관련

### 기본

- "API 호출 실패 시 어떻게 처리하시나요?"
  - ✅ **기대**: try-catch, 에러 상태 관리, 사용자 피드백, 재시도 옵션
  - ⭐ **가산**: HTTP 상태 코드별 처리, 에러 로깅
  - ❌ **레드플래그**: 에러 무시, console.log만 출력, 사용자 피드백 없음

- "사용자에게 에러를 어떻게 보여주시나요?"
  - ✅ **기대**: 토스트/알림, 인라인 에러 메시지, 에러 페이지
  - ⭐ **가산**: 에러 유형별 다른 UI, 복구 액션 제공
  - ❌ **레드플래그**: 기술적 메시지 그대로 노출, 에러 UI 없음

### 중급

- "ErrorBoundary의 역할과 한계점을 설명해주세요."
  - ✅ **기대**: 렌더링 에러 캐치, fallback UI 제공
  - ✅ **한계점**: 이벤트 핸들러/비동기 에러 못 잡음, 서버 컴포넌트 제한
  - ❌ **레드플래그**: ErrorBoundary 모름, 한계점 인지 못함

- "에러 처리를 계층화한다는 것은 무엇을 의미하나요?"
  - ✅ **기대**: 컴포넌트/페이지/앱 레벨 분리, 에러 전파 제어
  - ⭐ **가산**: 에러 유형별 처리 전략, 복구 가능 범위 설정
  - ❌ **레드플래그**: 계층화 개념 모름, 모든 에러 동일 처리

### 고급

- "프로덕션 환경에서 에러를 어떻게 모니터링하시나요?"
  - ✅ **기대**: Sentry, DataDog 등 에러 트래킹 도구, 소스맵 활용
  - ⭐ **가산**: 알림 설정, 에러 그룹핑, 사용자 컨텍스트 수집
  - ❌ **레드플래그**: 모니터링 경험 없음, 도구 모름 (시니어의 경우)

- "에러 복구 전략에 대해 설명해주세요."
  - ✅ **기대**: 재시도 로직, 폴백 데이터, graceful degradation
  - ⭐ **가산**: 지수 백오프, 서킷 브레이커 패턴
  - ❌ **레드플래그**: 복구 전략 없음, "에러 나면 새로고침"

## 4. 성능 관련

### 기본

- "웹 성능을 측정하는 방법을 알고 계신가요?"
  - ✅ **기대**: Lighthouse, Chrome DevTools, WebPageTest
  - ⭐ **가산**: 실제 사용자 모니터링(RUM), Performance API
  - ❌ **레드플래그**: 측정 방법 모름, "느리면 알아요"

- "Core Web Vitals에 대해 설명해주세요."
  - ✅ **기대**: LCP(로딩), FID/INP(상호작용), CLS(시각적 안정성)
  - ⭐ **가산**: 각 지표 개선 방법, 실제 최적화 경험
  - ❌ **레드플래그**: Core Web Vitals 모름, 지표 혼동

### 중급

- "번들 사이즈를 줄이기 위해 어떤 방법을 사용하셨나요?"
  - ✅ **기대**: 코드 스플리팅, 트리 쉐이킹, 라이브러리 교체, dynamic import
  - ⭐ **가산**: 번들 분석 도구 사용, 실제 감소 수치
  - ❌ **레드플래그**: 번들 사이즈 관심 없음, 방법 모름

- "코드 스플리팅은 언제 적용하는 것이 좋을까요?"
  - ✅ **기대**: 라우트 기반, 조건부 렌더링 컴포넌트, 대형 라이브러리
  - ⭐ **가산**: 프리로딩 전략, Suspense와 조합
  - ❌ **레드플래그**: 코드 스플리팅 모름, 적용 기준 없음

- "이미지 최적화를 어떻게 하시나요?"
  - ✅ **기대**: 적절한 포맷(WebP, AVIF), 크기 조정, lazy loading
  - ⭐ **가산**: next/image 활용, CDN, srcset
  - ❌ **레드플래그**: 최적화 방법 모름, 원본 그대로 사용

### 고급

- "성능 병목을 찾아본 경험이 있으신가요? 어떻게 해결하셨나요?"
  - ✅ **기대**: 프로파일링 도구 사용, 병목 원인 분석, 측정-개선-검증 사이클
  - ⭐ **가산**: 구체적인 개선 수치, 트레이드오프 고려
  - ❌ **레드플래그**: 경험 없음, 분석 없이 추측으로 최적화

- "렌더링 성능을 프로파일링해본 적 있으신가요?"
  - ✅ **기대**: React DevTools Profiler, Chrome Performance 탭
  - ⭐ **가산**: 플레임 그래프 해석, 리렌더링 원인 추적
  - ❌ **레드플래그**: 프로파일링 경험 없음, 도구 사용법 모름

## 5. 테스트 관련

### 기본

- "테스트를 왜 작성해야 한다고 생각하시나요?"
  - ✅ **기대**: 버그 예방, 리팩토링 안전성, 문서화 역할, 회귀 방지
  - ⭐ **가산**: 개발 속도 향상 (장기적), 자신감 있는 배포
  - ❌ **레드플래그**: "시간 낭비", "QA가 하면 됨"

- "E2E 테스트와 단위 테스트의 차이점은 무엇인가요?"
  - ✅ **기대**: 범위(함수 vs 전체 플로우), 속도, 신뢰도, 유지보수 비용
  - ⭐ **가산**: 테스트 피라미드, 각 레벨의 적정 비율
  - ❌ **레드플래그**: 차이점 모름, 테스트 경험 없음

### 중급

- "어떤 코드에 우선적으로 테스트를 작성하시나요?"
  - ✅ **기대**: 비즈니스 핵심 로직, 복잡한 조건문, 버그 발생 영역
  - ⭐ **가산**: 리스크 기반 테스트, 커버리지 vs 가치 판단
  - ❌ **레드플래그**: 기준 없음, "다 테스트" 또는 "안 함"

- "테스트하기 어려운 코드를 만났을 때 어떻게 하시나요?"
  - ✅ **기대**: 의존성 주입, 모킹, 코드 리팩토링으로 테스트 용이성 확보
  - ⭐ **가산**: 테스트 가능한 설계, 순수 함수 분리
  - ❌ **레드플래그**: "테스트 안 함", 해결 방법 모름

- "목(Mock)을 언제 사용하시나요?"
  - ✅ **기대**: 외부 의존성(API, DB), 느린 연산, 비결정적 동작
  - ⭐ **가산**: 모킹 과다 사용의 단점, 통합 테스트와 균형
  - ❌ **레드플래그**: 모킹 개념 모름, 모든 것을 모킹

### 고급

- "테스트 커버리지가 높으면 좋은 코드인가요?"
  - ✅ **기대**: "아니오" - 커버리지는 지표일 뿐, 테스트 품질이 중요
  - ⭐ **가산**: 의미 있는 assertion, 엣지케이스 포함 여부
  - ❌ **레드플래그**: "네, 높을수록 좋아요", 커버리지 맹신

- "TDD를 실무에서 적용해보신 적 있으신가요?"
  - ✅ **기대**: Red-Green-Refactor 사이클, 적용 경험 또는 견해
  - ⭐ **가산**: 상황별 적합성, 실제 적용 어려움과 해결책
  - ❌ **레드플래그**: TDD 개념 모름 (시니어의 경우)

## 6. 아키텍처/설계 관련

### 기본

- "이 프로젝트의 폴더 구조를 이렇게 설계한 이유가 무엇인가요?"
  - ✅ **기대**: 명확한 기준 제시, 일관성, 확장성 고려
  - ⭐ **가산**: 다른 구조와 비교, 트레이드오프 인지
  - ❌ **레드플래그**: 이유 없음, "그냥", 일관성 없는 설명

- "컴포넌트와 훅을 분리한 기준은 무엇인가요?"
  - ✅ **기대**: UI 로직 vs 비즈니스 로직, 재사용성, 테스트 용이성
  - ⭐ **가산**: 커스텀 훅 추출 기준, 관심사 분리
  - ❌ **레드플래그**: 기준 없음, 분리 안 함

### 중급

- "이 프로젝트를 확장한다면 어떤 부분을 먼저 개선하시겠어요?"
  - ✅ **기대**: 현재 한계점 인지, 구체적인 개선 방향, 우선순위 설정
  - ⭐ **가산**: 비용/효과 분석, 점진적 개선 전략
  - ❌ **레드플래그**: "완벽해서 개선할 게 없음", 개선점 파악 못함

- "같은 과제를 다시 한다면 다르게 할 부분이 있나요?"
  - ✅ **기대**: 자기 반성, 학습 포인트, 대안 제시
  - ⭐ **가산**: 시간 제약과 트레이드오프 인지
  - ❌ **레드플래그**: "없음", 성찰 부재

### 고급

- "마이크로 프론트엔드에 대해 어떻게 생각하시나요?"
  - ✅ **기대**: 개념 이해, 장단점, 적합한 상황
  - ⭐ **가산**: 실제 경험, Module Federation, 조직 구조와 연관성
  - ❌ **레드플래그**: 개념 모름 (시니어의 경우)

- "디자인 시스템을 구축해본 경험이 있으신가요?"
  - ✅ **기대**: 컴포넌트 라이브러리, 스타일 가이드, 일관성 유지
  - ⭐ **가산**: Storybook, 토큰 시스템, 버전 관리 전략
  - ❌ **레드플래그**: 경험도 이해도 없음 (시니어의 경우)

## 7. 협업/커뮤니케이션 관련

### 코드 리뷰

- "코드 리뷰를 어떻게 진행하시나요?"
  - ✅ **기대**: PR 크기 조절, 체크리스트, 건설적 피드백
  - ⭐ **가산**: 자동화 도구 활용, 리뷰 문화 개선 경험
  - ❌ **레드플래그**: 리뷰 경험 없음, "대충 봄"

- "코드 리뷰에서 가장 중요하게 보는 점은 무엇인가요?"
  - ✅ **기대**: 가독성, 버그 가능성, 설계, 테스트 여부
  - ⭐ **가산**: 맥락 파악, 대안 제시, 학습 기회
  - ❌ **레드플래그**: 스타일만 지적, 중요한 점 모름

- "피드백을 받았을 때 어떻게 대응하시나요?"
  - ✅ **기대**: 열린 자세, 논의 후 수용/반박, 학습 기회로 활용
  - ⭐ **가산**: 피드백 반영 후 공유, 패턴화
  - ❌ **레드플래그**: 방어적 태도, 무시

### 팀워크

- "팀 내에서 기술적 결정을 내릴 때 어떻게 하시나요?"
  - ✅ **기대**: 의견 수렴, 장단점 분석, 합의 도출
  - ⭐ **가산**: 문서화, ADR(Architecture Decision Records)
  - ❌ **레드플래그**: 독단적 결정, 의견 무시

- "의견 충돌이 있을 때 어떻게 해결하시나요?"
  - ✅ **기대**: 경청, 데이터 기반 논의, 공통 목표 확인
  - ⭐ **가산**: 실험/PoC로 검증, 타협점 찾기
  - ❌ **레드플래그**: 회피, 강압, 감정적 대응

- "주니어 개발자에게 기술을 설명해본 경험이 있으신가요?"
  - ✅ **기대**: 눈높이 맞춤, 예시 활용, 질문 유도
  - ⭐ **가산**: 멘토링 경험, 문서/가이드 작성
  - ❌ **레드플래그**: 경험 없음, "알아서 배워야지" (시니어의 경우)

## 8. 트러블슈팅 관련

### 디버깅

- "버그를 발견했을 때 어떤 순서로 디버깅하시나요?"
  - ✅ **기대**: 재현 → 범위 좁히기 → 원인 분석 → 수정 → 검증
  - ⭐ **가산**: git bisect, 로깅 전략, 체계적 접근
  - ❌ **레드플래그**: 무작위 수정, 체계 없음

- "재현이 어려운 버그를 어떻게 추적하시나요?"
  - ✅ **기대**: 로그 분석, 사용자 환경 파악, 조건 좁히기
  - ⭐ **가산**: 에러 모니터링 도구, 세션 리플레이
  - ❌ **레드플래그**: 포기, "재현 안 되면 안 고쳐요"

### 문제 해결

- "가장 어려웠던 기술적 문제와 해결 방법을 공유해주세요."
  - ✅ **기대**: 문제 정의 → 시도한 방법 → 해결책 → 학습 포인트
  - ⭐ **가산**: 문서화, 팀 공유, 재발 방지
  - ❌ **레드플래그**: 어려운 문제 경험 없음, 과정 설명 못함

- "성능 이슈가 발생했을 때 어떻게 접근하시겠어요?"
  - ✅ **기대**: 측정 → 병목 식별 → 가설 → 개선 → 검증
  - ⭐ **가산**: 프로파일링 도구 활용, 트레이드오프 고려
  - ❌ **레드플래그**: 추측으로 최적화, 측정 안 함

- "프로덕션에서 장애가 발생하면 어떻게 대응하시나요?"
  - ✅ **기대**: 영향 범위 파악 → 임시 조치 → 원인 분석 → 영구 수정
  - ⭐ **가산**: 포스트모템, 알림 체계, 롤백 전략
  - ❌ **레드플래그**: 당황, 대응 경험 없음 (시니어의 경우)

## 10. 과제 특화 질문

과제 분석 결과에 따라 커스텀 질문 생성:

### 설계 결정 관련

- "[특정 라이브러리]를 선택하신 이유가 무엇인가요?"
  - ✅ **기대**: 대안 비교, 선택 기준, 트레이드오프 인지
  - ❌ **레드플래그**: "그냥", "많이 써서", 대안 검토 안 함

- "[특정 패턴]을 사용하신 이유가 있으신가요?"
  - ✅ **기대**: 문제 해결 목적, 장점, 적합성
  - ❌ **레드플래그**: 패턴 이름만 알고 이유 모름

- "다른 방법도 있었을 텐데, 이 방식을 선택하신 이유는요?"
  - ✅ **기대**: 대안 인지, 비교 분석, 의사결정 과정
  - ❌ **레드플래그**: 대안 모름, "이것만 알아요"

### 개선점 관련

- "[발견된 문제]에 대해 어떻게 개선하실 것 같으신가요?"
  - ✅ **기대**: 문제 인정, 구체적 개선 방법, 실행 계획
  - ❌ **레드플래그**: 문제 부정, 개선 방법 모름

- "시간이 더 있었다면 어떤 부분을 추가하셨을까요?"
  - ✅ **기대**: 우선순위 판단, 구체적인 기능/개선점
  - ❌ **레드플래그**: "완벽해서 없음", 현실적이지 않은 답변

### 확장성 관련

- "사용자가 10배 늘어나면 어떤 문제가 생길까요?"
  - ✅ **기대**: 성능 병목 예상, 확장 포인트 식별
  - ⭐ **가산**: 구체적인 수치, 해결 방안
  - ❌ **레드플래그**: 문제 예상 못함, "괜찮을 거예요"

- "이 기능을 다른 페이지에서도 사용한다면 어떻게 하시겠어요?"
  - ✅ **기대**: 재사용 가능한 컴포넌트/훅 추출, 공통화 전략
  - ❌ **레드플래그**: 복사-붙여넣기, 재사용 고려 안 함
